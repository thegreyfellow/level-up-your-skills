Le problème

Vous avez déjà écrit ces phrases. Hier.

« Fais un plan avant de coder. » · « Pas de nouvelle dépendance. » · « Relis la spec. » · « Vérifie avant de dire fini. » · « Commit propre. »
  • Réécrites dans trois outils différents, souvent dans la même journée
  • Le contexte est un poisson rouge : chaque session repart de zéro
  • Votre expérience est la première victime de la fenêtre de contexte
1:30. Sondage rapide à main levée : qui a réécrit la même instruction à un agent cette semaine ? L'agent n'apprend pas de vos corrections — la seule mémoire fiable, c'est un fichier. Transition : donc écrivons le fichier.

Le déclic

Votre façon de travailler est un processus. Écrivez-le une fois.

  • Un skill = un fichier markdown + une description. C'est tout.
  • Pas de code · pas de plugin
  • Chargé au bon moment par l'outil que vous utilisez déjà
  • Versionnable, diffable, partageable — comme du code

Vous êtes développeurs : votre processus mérite un repo, pas des post-its dans un chat.

3:30. Vocabulaire : selon l'outil ça s'appelle skill, rules ou instructions — même principe, du texte injecté dans le contexte au bon moment. Le « bon moment », c'est la description : c'est elle que le modèle lit pour décider de charger le skill. On y reviendra, c'est le point n°1 de qualité.

Genèse

Comment ce skill s'est construit

  1. github.com/obra/superpowers Ça marche, mais ça consomme énormément de tokens.
  2. Découverte de ponytail. Les deux mélangés : toujours trop de tokens.
  3. Distillation. J'ai demandé à l'agent un skill minimal : les étapes clés de superpowers (obra) + l'esprit de ponytail (github.com/DietrichGebert/ponytail), avec l'échelle ponytail appliquée à chaque requête.
  4. Le processus a mûri. D'un agent qui me demande de l'aide à des subagents qui gèrent les sous-tâches et les problèmes, une fois le plan approuvé.

Je n'ai rien inventé. J'ai distillé — puis itéré sur du vrai travail.

5:30 — 4 min. Raconter l'histoire honnêtement, y compris les échecs : le premier skill était trop gourmand en tokens, le mélange avec ponytail aussi. La bascule : ne pas installer l'usine à gaz, mais demander à l'agent une version minimale, inspirée des étapes essentielles de superpowers (292k ★, excellent produit — installez-le si vous voulez la version complète) et de l'esprit de ponytail. L'échelle ponytail reste active à chaque requête : c'est ce qui limite les tokens. Puis le processus lui-même a évolué : au début il me sollicitait sans cesse, aujourd'hui les subagents traitent les sous-tâches et les blocages après l'approbation du plan. Message : un skill solide est un skill itéré.

Preuve

Mieux comprendre le métier et mieux s'expliquer aide à repérer ce qui manque dans un ticket, ou comment il s'intègre au code existant.

9:30 — 3 min. Être précis sur ce qui est dit : 4 mois, personnel et clients (pas de noms de clients). Le gain de quota est un ressenti : le même quota Copilot dure environ deux fois plus de tâches, voire plus. Ne pas inventer de chiffres de PR ou de tickets — je n'en ai pas. Le second effet, moins visible : le skill m'oblige à bien comprendre la tâche avant de coder, donc je repère plus vite les infos manquantes dans un ticket.

Le facteur clé

Ce qui rend l'agent autonome : la validation

  • Le travail dur : du TDD et une validation automatisée qu'on peut lancer en une commande
  • Salesforce : sf project deploy start --dry-run --test-level RunSpecifiedTests --tests MaClasseTest
  • Node : npm test

Un projet sans tests = un agent sans garde-fou. Préparez le projet avec des tests : c'est ce qui rend les agents autonomes possibles aujourd'hui.

12:30 — 3 min 30. Faire le lien avec la gate n°2 : « DONE » = la commande de vérification passe. Sans commande de validation automatisée, il n'y a rien à faire passer, donc l'humain redevient le test. C'est là que se joue l'autonomie. Exemples : Salesforce — un déploiement en dry-run limité à des tests ciblés (sf project deploy start --dry-run --test-level RunSpecifiedTests --tests MaClasseTest ; sf project deploy validate fait la même vérification et permet un quick-deploy ensuite) ; Node — npm test. Conseil concret : avant de brancher un agent sur un projet, préparer les tests et la commande.

Pourquoi ça marche — 1/5

Les deux gates : jamais d'auto-approbation

  • L'agent s'arrête et attend : le plan avant le code, la sortie de tests fraîche avant « DONE »
  • « DONE » = la commande de vérification passe — rien d'autre ne compte
  • Le contrôle humain aux deux seuls points irréversibles : avant d'écrire, après l'écriture

Le problème n°1 des agents : optimiser pour avoir l'air DONE. Une gate EST la spécification de l'arrêt.

21:00. Le cœur du skill. Sans gate, l'agent enchaîne plan→code→« DONE ! » dans le même souffle et vous découvrez le résultat. Avec : vous voyez le plan quand il coûte encore 0 ligne de code. « Just do it » compte comme approbation — c'est écrit.

Pourquoi ça marche — 2/5

Classer avant de foncer

Spikequestion de faisabilité : la réponse est le livrable, le code est jetable
→
Boundedchangement cadré : design court, en chat
→
Architecturalnouveau sous-système : 2-3 options + recommandation

Process plus léger ← → process plus lourd · une tâche peut seulement aller vers la droite

  • Complexité cachée découverte en route → la tâche passe à la catégorie à droite, jamais à gauche (un Spike qui devient Bounded, un Bounded qui devient Architectural)
  • « Trop simple pour un design » n'existe pas — un design peut tenir en 2 phrases
  • « X le couvre déjà » est une fin valide
24:00. La classification évite les deux pathologies : sur-traiter une petite tâche (cérémonie inutile) et sous-traiter une grosse (l'agent fonce sur 3 fichiers). La règle « on ne peut qu'aller vers la droite » (du plus léger au plus lourd) protège contre la complexité cachée découverte en route : une tâche Bounded qui se révèle Architectural est reclassée, on ne la minimise pas. Et non, tout doit passer par un design — même de deux phrases. C'est ça qui tue le « trop simple pour… ».

Pourquoi ça marche — 3/5

Build : un subagent par tâche

  • 1 tâche = 1 subagent au contexte frais. Le prompt = son monde entier
  • Contrat de rapport : DONE · DONE_WITH_CONCERNS · NEEDS_CONTEXT · BLOCKED
  • Le controller relit le diff. Il ne code jamais.
  • Seuils : 3 tours de fix → modèle plus fort · 5 → re-plan · ~150 lignes → re-approbation

Votre outil n'a pas de subagents ? (Copilot, Cursor…) Même discipline en inline : le prompt de tâche reste le contrat, la revue du diff reste obligatoire.

26:30. Contexte frais = pas de pollution croisée entre tâches et pas de compaction en cours de route. Le controller reste stratégique : coordination, revue, prochain plan. Le contrat de rapport force le subagent à signaler au lieu de bluffer. Mentionner la dégradation inline pour les outils sans subagents (Copilot, Cursor).

Pourquoi ça marche — 4/5

ponytail : écrire moins

L'échelle, du haut vers le bas — on s'arrête au premier barreau qui tient :

besoin réel ? → déjà dans le code ? → stdlib ? → plateforme ? → dépendance déjà installée ? → une ligne ? → le minimum

  • Pas d'abstraction spéculative, pas de factory pour un produit
  • Suppression > ajout
  • Chaque raccourci assumé est annoté (ponytail:) avec son ceiling
29:30. Je l'ai en plugin OpenCode, mais honnêtement : l'essentiel tient en 10 lignes dans votre skill. C'est l'anti-pattern n°1 des agents : l'usine à gaz spéculative. Le modèle adore écrire des factories « au cas où ». Ces 10 lignes là sont le meilleur ratio lignes/valeur de tout le fichier. ⏱ En retard ? Cette slide et la suivante (tokenjuice) se compressent à ~30 s chacune — jamais le trio gates/classification/build avant elles.

Pourquoi ça marche — 5/5

tokenjuice : le contexte, c'est le budget

  • Sorties de commandes tronquées (head + tail), ANSI strippé, doublons tués
  • Ne relit pas un fichier déjà dans le contexte
  • Résultat : la session controller tient des heures sans compaction

C'est ce qui rend l'approche multi-subagents viable économiquement : un controller propre peut orchestrer toute une journée.

La suite

Prochaine itération : l'orchestrateur

/workflow gère un ticket. L'orchestrateur en gère plusieurs, en parallèle :

  • Brainstorm et plan remontent d'un niveau : il reçoit une liste de tickets (ou un accès MCP à Jira) et on les passe un par un ensemble
  • Il ouvre une session tmux par ticket, dans un worktree et une branche séparés, qui exécute /workflow
  • Moi : le brainstorm/plan, la review, et les tickets qui remontent un problème

Les skills vont continuer d'évoluer : les modèles progressent et auront besoin de moins d'explications. Un skill est un document vivant.

36:30 — 3 min 30. C'est une direction, pas un produit fini : ne pas dire que c'est livré. Les sessions de ticket sont de vraies sessions (pas des subagents imbriqués) parce que les subagents sont en lecture seule et qu'on n'interagit avec eux que via l'agent principal ; pour garder le contrôle sur chaque ticket, on ouvre de nouvelles sessions au niveau workflow. Je peux intervenir quand un ticket remonte un problème. Matière pour les questions si besoin : plan dans un fichier (docs/plans/.md) pour survivre à la compaction, hook git pre-commit qui bloque les commits sur main, protocole de dispatch remonté au début de la phase 4. Puis ouvrir les questions (20 min).

Étape 1

Vos trois règles 5 min

  • Ouvrez fr/exercice/template.md, recopiez-le dans votre outil (fiche par-outil/ correspondante)
  • Vos pétages de plomb quotidiens → 3 règles impératives

Exemples : « jamais de dépendance sans me demander » · « trace tous les appelants avant de fixer » · « tests frais avant de dire fini »

Étape 1 — 16:30→21:30. La question à poser en circulant : « qu'est-ce que tu as réécrit à un agent cette semaine ? » — c'est TA règle. Trois maximum : un skill n'est pas un manuel, c'est un manifeste.
Étape 2

Vos deux gates 5 min

  • Où voulez-vous décider ? Avant le code ? avant le commit ? avant le push ?
  • Formulez l'arrêt de façon explicite : « arrête-toi et attends mon OK »
  • Deux gates suffisent. Trois = friction, une = roulette russe.
Étape 2 — 21:30→26:30. Les gates sont la partie la plus personnelle : le backender prudent mettra une gate avant push, le gens du front avant toucher au design system. Insister sur la formulation impérative de l'arrêt — un vœu pieux (« idéalement valide avec moi ») n'est pas une gate.
Étape 3

Votre format de build 5 min

  • Inline ou subagents ? (selon votre outil — les deux se défendent)
  • TDD : oui / non / « un check runnable pour la logique non triviale »
  • Branches, commits : quelle hygiène minimum ?

Copilot / Cursor : mode inline ou agent tasks · Claude / OpenCode : subagent par tâche

Étape 3 — 26:30→31:30. Pas de dogme TDD ici : la version minimale honnête c'est « un check runnable pour la logique non triviale ». Ce qui compte : que « DONE » ait une définition vérifiable par commande.
Étape 4

Le micro-skill 7 min

  • Prenez UNE techno que vous touchez tous les jours (React ? Terraform ? votre CI ?)
  • ≈ 20 lignes : conventions maison, pièges, commande de vérification
  • La description = le déclencheur — soignez-la plus que le corps

C'est la mise à niveau : générique (workflow) → spécifique (techno). Cf. fr/exercice/exemple-micro-skill.md

Étape 4 — 31:30→38:30. La pièce maîtresse de l'exercice : c'est LÀ qu'ils réalisent que « faire un skill » = 20 lignes de conventions qu'ils ont dans la tête depuis des années. Faire lire l'exemple react à voix haute si la salle cale. Les bons déclencheurs : « dès qu'on touche à src/components », « dès qu'une migration est impliquée ».
Étape 5

Testez — maintenant 3 min

  1. Nouvelle session dans votre outil
  2. Une mini-tâche réelle : « nouvelle tâche : … »
  3. L'agent doit s'arrêter à la première gate. Sinon → c'est la description qu'il faut réécrire

Un skill non testé n'existe pas.

Étape 5 — 38:30→41:30. Le test, c'est le produit. 90 % des « mon skill ne marche pas » = une description vague. Faire réécrire deux descriptions en direct, en comparant avant/après — effet immédiat garanti. Plan B si un outil ne répond pas (wifi capricieux, trial/quota mort) : jumeler la personne avec un voisin — elle lit le skill du voisin, aide à affiner sa description, et teste le sien dès que son outil revient. Personne ne reste inactif.

Fiche récap

Ce qui fait un bon skill

  • La description est le déclencheur — c'est elle que le modèle lit pour décider de charger
  • Impératif, mesurable, pas de prose
  • < ~150 lignes — sinon découpez en deux skills
  • Testé sur une vraie tâche, dans une vraie session
