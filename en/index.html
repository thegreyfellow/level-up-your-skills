The realization

The way you work is a process. Write it down once.

  • A skill = one markdown file + one description. That's it.
  • No code · no plugin · no subscription
  • Loaded at the right moment by the tool you already use
  • Versionable, diffable, shareable — like code

You're developers: your process deserves a repo, not sticky notes in a chat.

4:30. Read the diagram at a high level. The two red gates = the only two moments where everything stops and a human decides. Between them: full autonomy. That's the contract: autonomy in exchange for checkpoints.

Why it works — 1/5

The two gates: never self-approve

  • The agent stops and waits: the plan before code, fresh test output before "done"
  • "Done" = the verification command passes — nothing else counts
  • Human control at the only two irreversible points: before writing, after writing

The #1 agent problem: optimizing to look done. A gate IS the specification of stopping.

6:00. The heart of the skill. Without a gate, the agent chains plan→code→"done!" in one breath and you discover the result. With one: you see the plan while it still costs 0 lines of code. "Just do it" counts as approval — it's written down.

Why it works — 2/5

Classify before charging ahead

  • Spike — an answer, not code. Throwaway by definition.
  • Bounded — a well-scoped change. Short design, in chat.
  • Architectural — new subsystem. 2-3 options + recommendation.
  • The ratchet only goes one way: hidden complexity upgrades, never downgrades
  • "Too simple for a design" does not exist — a design can be 2 sentences
  • "X already covers it" is a valid ending
7:30. Classification avoids both pathologies: over-processing a small task (useless ceremony) and under-processing a big one (the agent charges into 3 files). The ratchet protects against hidden complexity discovered along the way. And no — every task gets a design, even a two-sentence one. That's what kills "too simple to…".

Why it works — 3/5

Build: one subagent per task

  • 1 task = 1 subagent with fresh context. The prompt = its entire world
  • Report contract: DONE · DONE_WITH_CONCERNS · NEEDS_CONTEXT · BLOCKED
  • The controller reviews the diff. It never writes code.
  • Thresholds: 3 fix rounds → stronger model · 5 → re-plan · ~150 lines → re-approval

Your tool has no subagents? (Copilot, Cursor…) Same discipline inline: the task prompt stays the contract, the diff review stays mandatory.

9:00. Fresh context = no cross-task pollution and no mid-flight compaction. The controller stays strategic: coordination, review, next plan. The report contract forces the subagent to report instead of bluffing. Mention the inline degradation for other tools — important for the workshop half.

Why it works — 4/5

ponytail: write less

The ladder, top down — stop at the first rung that holds:

real need? → already in the codebase? → stdlib? → platform? → already-installed dependency? → one line? → the minimum

  • No speculative abstractions, no factory for one product
  • Deletion > addition
  • Every deliberate shortcut is annotated (ponytail:) with its ceiling
10:30. I run it as an OpenCode plugin, but honestly: the essence fits in 10 lines in your skill. It's agent anti-pattern #1: the speculative factory. Models love writing factories "just in case". Those 10 lines are the best lines/value ratio in the whole file.

Why it works — 5/5

tokenjuice: context is the budget

  • Command output truncated (head + tail), ANSI stripped, duplicates killed
  • Never re-reads a file already in context
  • Result: the controller session holds for hours without compaction

This is what makes multi-subagent economically viable: a clean controller can orchestrate a whole day.

Installs on all five tools in this room — Claude Code, Cursor, Copilot, OpenCode (stable), Antigravity (beta): tokenjuice install <tool>

Step 1

Your three rules 5 min

  • Open en/exercise/template.md, copy it into your tool (matching per-tool/ sheet)
  • Your daily blowups → 3 imperative rules

Examples: "never add a dependency without asking me" · "trace every caller before fixing" · "fresh tests before saying done"

Step 1 — 16:30→21:30. The question to ask while walking around: "what did you rewrite to an agent this week?" — that's YOUR rule. Three maximum: a skill is not a manual, it's a manifesto.
Step 2

Your two gates 5 min

  • Where do you want to decide? Before code? before commit? before push?
  • Make the stop explicit: "STOP and wait for my OK"
  • Two gates is enough. Three = friction, one = Russian roulette.
Step 2 — 21:30→26:30. Gates are the most personal part: a careful backend dev will gate before push, frontend folks before touching the design system. Insist on the imperative wording of the stop — a wish ("ideally check with me") is not a gate.
Step 3

Your build format 5 min

  • Inline or subagents? (depends on your tool — both are defensible)
  • TDD: yes / no / "one runnable check for non-trivial logic"
  • Branches, commits: what minimum hygiene?

Copilot / Cursor: inline mode or agent tasks · Claude / OpenCode: one subagent per task

Step 3 — 26:30→31:30. No TDD dogma here: the honest minimal version is "one runnable check for non-trivial logic". What matters: "done" has a definition checkable by command.
Step 4

The micro-skill 7 min

  • Pick ONE technology you touch daily (React? Terraform? your CI?)
  • ≈ 20 lines: house conventions, pitfalls, verification command
  • The description = the trigger — polish it more than the body

This is the upgrade path: generic (workflow) → specific (tech). See en/exercise/example-micro-skill.md

Step 4 — 31:30→38:30. The centerpiece of the exercise: THIS is where they realize "making a skill" = 20 lines of conventions they've carried in their head for years. Read the React example aloud if the room stalls. Good triggers: "whenever we touch src/components", "whenever a migration is involved".
Step 5

Test — now 3 min

  1. New session in your tool
  2. One real mini-task: "new task: …"
  3. The agent must stop at the first gate. Otherwise → rewrite the description

An untested skill doesn't exist.

Step 5 — 38:30→41:30. The test IS the product. 90% of "my skill doesn't work" = a vague description. Rewrite two descriptions live, comparing before/after — guaranteed immediate effect.
